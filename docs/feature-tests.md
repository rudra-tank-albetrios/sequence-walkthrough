# Feature tests

What proves each row of plan section 10 (`docs/IMPLEMENTATION-PLAN.md`). Each phase adds its own rows on its branch; the lead merges the table. The last column says what only a real model run can show, so nobody reads a unit test as more than it is.

| Area | Must be proven | Proof in the repository | Only a real model run can show |
|---|---|---|---|
| Skills | Each trigger loads the right skill. Layers match Express, NestJS or Next.js, Django and feature-folder samples. | `tools/build-skills/src/skill-text.test.ts` (`checkFrontMatter`): each skill's description holds its own trigger phrases and none of the other skill's; the build stops otherwise, and `tools/check-budgets` keeps `SKILL.md` under 8 KB and 15 KB and each description under 1,024 characters. `tools/build-skills/src/fixtures.test.ts`: for the five samples in `skills/fixtures` (Express, NestJS, Next.js, Django, feature folders) the expected diagram draws the sample's layers in order, each once, and every `@layer` names a folder or file on the path that `skills/shared/references/layer-naming.md` maps. `tools/build-skills/src/build.test.ts`: the built `SKILL.md` files state the standing rules (chat only, middleware a layer, Easy keeps layers, Scoped means only that part, side parts, links only to opened code, `@unconfirmed`, `@threat` only from the code). | That Claude loads only the matching skill for a phrase, and that it maps a project's folders to those layers itself. The one measured run (`docs/runs/demo-store-seq-diagram.md`) drew the demo store's 20 layers in the same order as the demo's own `flows/place-order.mmd`. |
| Reading | No file read twice, and a good README reduces code reads | `tools/build-skills/src/run-evidence.test.ts`: the transcript reader lists the files a run opened in order, the repeats, whether the README came first, and files outside the project. Applied to the measured run on `examples/demo-store` (`docs/decisions.md`, Phase 5): 31 files opened, none twice, README first. | Fewer code reads with a good README: that needs two runs on one sample, with and without its README. `skills/fixtures/express-shop` and `feature-shop` carry a README that covers the flow; `nest-shop`, `django-shop` and `next-shop` have none, so the comparison is ready to run with `node tools/build-skills/src/run-evidence-cli.ts <transcript> <sample>`. |
| Accuracy | Paths, statuses and fields match the code | `tools/build-skills/src/fixtures.test.ts`: every expectation in a sample's `expected.json` is anchored to a `[file, text]` that exists in the sample's code; the expected diagram's request path, statuses, messages, request and reply fields, names and links match those expectations; every `@ref` resolves under the sample (the validator's `--root` check); and nine ways to drift (a wrong status, path or field, a link off the path or to a missing line, middleware as a side part, a layer drawn twice, no `autonumber`, a label Mermaid would split) are each caught by the validator or by `checkAccuracy`. On the measured run, the validator with `--root examples/demo-store` found 0 errors, 0 warnings and every code link resolving. | That a model's diagram matches field by field: the measured run's paths, statuses and fields were checked only by the validator's link check, not against an `expected.json` for the demo store. Running a skill on a sample and passing its reply through `checkAccuracy` is the test for that. |
