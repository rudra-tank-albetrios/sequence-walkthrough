# Decisions

Decisions the plan (`docs/IMPLEMENTATION-PLAN.md`) does not already make, one or two lines each, newest last.

## Phase 1: foundation (2026-10-30)

- **TypeScript 5.9, not 7.** TypeScript 7 (the native compiler) is current on npm, but typescript-eslint supports only versions below 6.1. The 5.9 line is pinned until the lint tooling catches up; Dependabot will propose the bump and CI will tell us when it works.
- **ESLint 10 without eslint-plugin-jsx-a11y.** The a11y plugin does not support ESLint 10. Accessibility is checked where it matters, on the rendered page, with axe-core in the Playwright tests.
- **Workspace packages export their TypeScript source.** `@swv/core` and `@swv/ai` point `exports` at `src/index.ts`. Vite bundles them into the app, Vitest reads them directly, and Node 24 runs the tools' `.ts` files without a build step. `erasableSyntaxOnly` is on so Node's type stripping always works. Nothing in `packages/` needs to be compiled before use.
- **Package scope `@swv`.** Short, and it matches the `swv:` prefix the viewer has always used for browser storage.
- **Content Security Policy as a `<meta>` tag.** GitHub Pages cannot set response headers. The tag is added only to production builds, because the Vite dev server and React refresh need an inline script while developing.
- **Python stays only in the deploy workflow** until Phase 4 switches hosting to the new app. `npm run verify` has no Python step.
- **Playwright runs a phone project (Pixel 7)** in addition to Chromium, Firefox and WebKit, because the plan requires a phone layout.
- **Gitleaks through the official GitHub Action.** It is free for repositories owned by a user account, which this one is.
- **Repository settings:** squash and rebase merges are turned off so every merge is a merge commit (plan section 1, rule 7); branches are deleted on merge; GitHub secret scanning, push protection, Dependabot security updates and private vulnerability reporting are turned on. All are free on a public repository.
- **Firefox runs in CI only on the build machine.** Playwright's Firefox build does not start on the Windows machine used for the build ("side-by-side configuration is incorrect", a missing system runtime), and installing system components is out of scope. CI on Ubuntu runs all four browser projects; locally `SWV_E2E_PROJECTS=chromium,webkit,phone npm run verify` runs the rest. The variable is ignored in CI.
- **A ruleset ("Protect main") instead of classic branch protection.** It requires a pull request, an up-to-date branch, merge commits only, and the checks `verify`, `gitleaks`, `CodeQL (javascript-typescript)` and `CodeQL (actions)` (the CodeQL job is a matrix, so each language reports its own check). It also blocks force pushes and deletion. No required review, since GitHub does not let an account approve its own pull request. Renaming a job or the matrix changes the check names and must be mirrored in the ruleset.

## Phase 2: core package and demo store (2026-10-30)

- **Golden files come from the version 2 parser running in a real browser.** `tools/golden` opens the version 2 page in Playwright, feeds Mermaid 12.2.0 to it from Node (a headless page opened from disk cannot reach the CDN reliably) and records `Annotations.parse`, Mermaid's own view of the arrows and `buildFlow` for every fixture in `packages/core/fixtures`. It is a migration tool, not part of `npm run verify`. Phase 4 removed the tool; its section below says how to record a new golden.
- **Version 3 reads the Mermaid sequence syntax itself** (`packages/core/src/sequence.ts`) instead of asking Mermaid for its parsed messages. The browser still renders with Mermaid, but the parser now runs in Node, in the skills' validator and in tests without a DOM, and arrows map to source lines directly. The goldens prove it reads participants, arrows, arrow styles and block nesting exactly as Mermaid 12.2.0 does for every fixture.
- **Six recorded differences from version 2**, each named in `packages/core/src/golden.test.ts`: (1) Mermaid's internal entity placeholders (`ﬂ°°59¶ß`) no longer leak into labels; `#59;` decodes to `;`. (2) A side part used twice on one step lists that step once. (3) `endings` are step indexes, not copies of step objects. (4) When Mermaid refuses the code, version 3 still reads participants and blocks and reports the exact line (`flow.syntax`), where version 2 fell back to a regex read. (5) The eight backend layer kinds the plan names (app, router, validator, controller, serializer, repository, eventbus, cron) are recognised, plus `dto`; version 2 on `main` knew ten kinds. (6) `main` is always present.
- **A bare `;` splits a line into statements**, because that is what Mermaid's lexer does (`A->>B: hi; B-->>A: ok` draws two arrows). Both scanners split the same way, so arrows and annotations stay paired. Text after a `;` that is not a statement is reported as `semicolon`.
- **Mermaid-incompatible lines are reported by the parser** as `flow.syntax` with the codes `semicolon`, `no-colon`, `unknown-line`, `block` and `keyword-alias` (the codes `validate.py` used), kept apart from the viewer's `flow.lint` so the lint shape stays identical to version 2.
- **Half-arrow styles (`-/`, `-|`, `-\`)** are parsed as arrows but typed as open arrows; Mermaid's exact LINETYPE numbers for them were not verified and no fixture uses them.
- **Demo flow error replies are drawn from App to API Client** (`APP-->>API: 401 Unauthorized`), not from the middleware or validator that produced them, so each reply pairs with the main request and shows as one of its endings. The step text says which layer produced the response.
- **The demo's in-memory database is described with the SQL it stands in for** in `@payload.sql` lines, each marked "an in-memory table, doing the job of", so the Data tab shows the tables touched without claiming the demo runs SQL.
- **`process.stdout.write` stays allowed.** The raw-HTML lint rule now bans only `document.write`/`writeln`, not every `.write(` call. It requires a pull request, an up-to-date branch, merge commits only, and the checks `verify`, `gitleaks`, `CodeQL (javascript-typescript)` and `CodeQL (actions)` (the CodeQL job is a matrix, so each language reports its own check). It also blocks force pushes and deletion. No required review, since GitHub does not let an account approve its own pull request. Renaming a job or the matrix changes the check names and must be mirrored in the ruleset.

## Phase 3: React viewer (2026-10-31)

- **The demo flow is the default diagram** (`examples/demo-store/flows/place-order.mmd`, imported at build time) and the "Load example" code, replacing the payment example version 2 shipped. The plan's section 8.12 asks for this; doing it now keeps one default for the rest of the build.
- **One parser for the viewer.** The page parses with `@swv/core` and uses Mermaid only to draw. Arrow N in the code is drawn arrow N, so the SVG mapping is by position, as in version 2, and a count mismatch shows a toast instead of guessing.
- **Mermaid output goes through DOMPurify** before it reaches the page, in the one component (`features/viewer/DiagramSvg.tsx`) the lint rule allows. The `name` attribute Mermaid puts on participants and the `<style>` element with the theme are kept; scripts, event handlers and links are not.
- **Content Security Policy:** `connect-src 'self' https: http://localhost:* http://127.0.0.1:*`, because Ask AI calls whichever model URL the user chose and Ollama runs on localhost over http. Scripts stay `'self'`.
- **Colours use `light-dark()`**, so every token is declared once and the theme choice only switches `color-scheme`. The user-interface theme follows the system, as in version 2; the diagram theme is the setting the user picks.
- **Feature folders own their screens; shared state lives in Zustand stores under `shared/state`.** Features talk through the stores (`ui` flags such as `askOpen`, `importOpen`) and never import each other; `dependency-cruiser` checks it. The one hand-over outside the stores is the right-click menu's "Ask AI: what is X?", which leaves the question in `sessionStorage` under `swv:ask:prefill`.
- **The keyboard map is the shell's** (`app/useGlobalKeys.ts`), including the Esc cascade in version 2's order; widgets handle only their local keys.
- **Version 2 behaviours kept as they really were, not as the README said:** `Home` goes to step 1 (the overview is reached with Esc or at load), and the Claude provider has no consent step of its own in the page (the host's prompt is the consent).

## Phase 10: quick day recap (2026-10-31)

- **The analysis runs on a click, never on opening.** The panel first says what would be sent (the questions, the person's answers and the correct answers, to their own model), so browsing periods spends no tokens and reopening only reads what is saved. The plan says "the user's model groups mistakes" without saying when; asking first is the choice that fits plan section 4.
- **A saved analysis is kept for each period and flow choice** in IndexedDB (`swv:recap:analysis`, the 30 latest, validated with Zod when loaded; a damaged entry counts as none). It lists the id and date of every mistake it covered.
- **"New mistakes" means an id the saved analysis has not seen, or a newer date on one it has,** so missing a known question again counts. A correct answer or a period running out does not end it: a group with no mistakes left is hidden, and when none is left the panel asks again. `Saved analysis` always means nothing was sent to show it.
- **At most 20 mistakes and 6,000 bytes go in the prompt, the most missed first,** with each field clipped. That keeps the request near the 1,500 tokens a flow summary may cost, and the saved line says when only part of the list was covered. The diagram code is never sent.
- **A reply can only be displayed.** Only `title`, `points` and `mistakes` are kept, as plain text on one line and within fixed sizes, and a number in `mistakes` counts only when it names a mistake that was sent. Retry topics come from the stored mistakes, never from a reply.
- **The sample recap shows only while the person has no mistakes of their own and the unedited demo flow is on screen,** because its steps and answers are true only for that code. It says it is a sample and sends nothing, even with a model set up. If a person later fixes all their mistakes, the sample comes back, and its banner stays true.
- **"Today" is the local calendar day, and "last 7 days" is today plus the six days before it,** so the counts match the dates a person sees, whatever the hour.
- **`Retry my mistakes` closes the recap first.** The hand-over to the quiz is only the `swv:quiz:retry` session key and the `quizOpen` flag, as agreed with phase 9, because features cannot import each other.
- **The recap's code loads when it first opens** (`lazy`), so its share of the model package and the sample stay out of the first load.
## Phase 4: cutover (2026-10-31)

- **The website is built from `apps/web/dist` by Node.** `deploy-pages.yml` has two jobs: `build`, read-only with no npm cache, so no dependency code runs next to a deploy token, and `deploy`, with only `pages: write` and `id-token: write`. `actions/configure-pages` went with Python: it only reads settings the relative `base: './'` does not need, and `deploy-pages` does not depend on it. Same URL, because the repository name and the Pages source did not change.
- **Version 2's code stays in git history, and `tools/golden` is removed.** Both tools ran the version 2 page, so they cannot outlive it, and carrying code that fetches old files out of git would be more to maintain than the recipe below. The goldens in `packages/core/fixtures` are checked in and `golden.test.ts` keeps reading them.
  - `398d08e` holds the last version 2 app (`src/`, `build.py`); both are byte-identical from there to the commit before this cutover.
  - `debfb9b` (the merge of Phase 2) holds that app and the recorder. To record a golden for a new fixture: `git worktree add ../swv-v2 debfb9b`, then in it `npm ci`, `python build.py`, copy the `.mmd` into `packages/core/fixtures`, `node tools/golden/src/index.ts <name>`, and copy the `.golden.json` back.
  - `8ea0b62` also holds `tools/golden/src/compare.ts`, the old-against-new screenshot tool.
- **`dist/` and `dist-claude/` were never tracked**, so the only clean-up was the ignore files.
- **The one-file build is two pages.** `npm run build:single -w @swv/web` (`vite build --mode single`, also part of `npm run build`) writes to `apps/web/dist-single/`. Version 2 had the same pair: `sequence-walkthrough.html` is a whole document to open from disk, as version 2's `dist/index.html` was, and `sequence-viewer.html` is that page without doctype, `html`, `head`, `body` or policy, as `dist-claude/` was, because the Artifact tool wraps a page in its own skeleton. The build stops if any file is left outside the page.
- **The one-file page's policy allows one script, by hash.** `script-src 'self'` would block the inlined script, and `'unsafe-inline'` would let any injected script run, so `vite-plugins/oneFilePage.ts` computes the SHA-256 of the script after inlining and allows only that. The rest is stricter than the website's: `default-src 'none'`, and images and fonts only from `data:` and `blob:`. `connect-src` stays open to `https:` and localhost because Ask AI calls the model URL the user chose. `style-src 'unsafe-inline'` stays because Mermaid writes styles into its SVG. The website's policy is unchanged, and `e2e/hosted.spec.ts` fails if it moves.
- **The artifact page has no policy of its own, because it must not have one.** The host sets the policy, and its runtime loads a capability's module when `claude.use()` is called (runtime contract 0.2.94), so a page policy allowing only our hash could block the Claude provider and the save dialog. For the same reason that file is never put on the website: with no policy, on the site's origin, it would sit next to people's stored API keys.
- **People get the one-file viewer from `sequence-walkthrough-one-file.zip`, published next to the website**: `https://rudra-tank-albetrios.github.io/sequence-walkthrough/sequence-walkthrough-one-file.zip`. It holds both pages and a short `README.txt`. A zip is inert on the site's origin, is about a third of the size, and needs no release to exist. `npm run build` copies it next to the site, so GitHub Pages and Netlify publish the same thing. The guide dialog on the website links to it. Phase 12 can also attach it to the `v3.0.0` release.
- **Inside the one-file page, nothing fetches.** The skill kit is carried in the page as text (`__SKILL_KIT__`, only in that build), as version 2 embedded it, and export code reads the fonts from their `data:` URLs, so `connect-src` does not need `data:`.
- **`sequence-walkthrough.zip` stays on the website and now holds the skill kit.** Version 2 published it and links to it exist, but `tools/build-skills` no longer makes a skill of that name, so `skillKit.ts` publishes the kit under both addresses.
- **The Claude provider handles the runtime's real answers.** `claude.use('sample')` resolves `null` when a view cannot run it, and a refusal is a plain `{ code, message }`, so the panel says so in words. `request.ts` is `main`'s with only this added back on top, because `request.test.ts` holds this behaviour to account and `main`'s file alone fails it. The artifact tests run against a stub of runtime contract 0.2.94, because a real host cannot be driven from a test.
- **Flowchart, class and state labels.** The one-file test for other diagram types found that DOMPurify removed `<foreignObject>`, where Mermaid puts those labels, so they drew with no text on the website too. Allowing that element let hostile markup reach the page and failed `security.spec.ts`, so `features/viewer/mermaid.ts` sets `htmlLabels: false` and Mermaid draws those labels as SVG text, with `<foreignObject>` still refused.
- **The link preview tags came back.** Version 2's page had `og:type`, `og:title` and `og:description`, and the new `index.html` had lost them. They are plain text with no address in them, so both builds carry them.
- **Prettier has never checked a `src` folder, and this phase does not change that yet.** `.prettierignore`'s `src/` line, meant for the version 2 app, matched every `src` folder at any depth. Removing it would reformat over 100 files and conflict with every open build branch, so it is now an explicit `**/src/` line with a comment. When no build branch is open, delete that line and run `npm run format` in one commit.
- **The merge with `main` (PR 8 and the skills).** `main` wins on viewer and feature code, and the cutover wins on removing version 2. `skillKit.ts` is `main`'s, with `readSkillKit` exported so the one-file build can carry the same kit (`__SKILL_KIT__`, in `vite.config.ts`). `zipEntries` moved to `oneFilePage.ts`, its only remaining user.
- **The one-file page escapes NUL bytes.** The bundler writes a `\0` in a string as a raw byte. The HTML parser reads that as U+FFFD, so the browser's hash of the inlined script differed from the policy's and the page did not start. `npm run check` opens only the website, so it passed anyway; `e2e/one-file.spec.ts` found it. `oneFilePage.ts` now writes the byte as `\u0000` before hashing.
- **Known failures after the merge, outside `npm run check`:** `e2e/hosted.spec.ts` on `sequence-walkthrough.zip` and `e2e/one-file.spec.ts` on other diagram types (no label text). Both are the open points above.

## Phase 3, continued: parity tests, security and the golden compare (2026-10-31)

- **Golden compare done before the old app goes** (plan 7.2). `tools/golden/src/compare.ts` shot the demo flow in both apps, light, dark and phone, at the overview and at step 5 (`tmp/compare/*.png`, not committed). Every control, chip, band, chapter, card and notice of version 2 is present in version 3. The differences are visual and small: the top bar is a few pixels taller and marks the active view with a filled tab; the overview card starts about 25 px lower, so its layer list scrolls a little earlier; the card's Ask button reads "? Ask AI" instead of "?". Nothing is missing, so the old app can be removed in Phase 4.
- **Version 2 behaviours kept where a draft test assumed otherwise:** with the chapter lock on, Left from step 1 still goes to the overview (only a chapter edge toasts); the Behind popover lists kinds in sorted order; two `@payload.headers` lines give two labelled boxes; the open code panel covers the canvas Code button, so the panel's × or `C` closes it; the Ask AI footer names Ollama "Ollama on this computer"; the canvas notice (spotlight, path) belongs to the canvas and is not shown over the table view.
- **Small departures from version 2, on purpose:** the "too short to follow" toast uses typographic quotes like the glossary toast and the right-click menu; the payload and schema boxes start closed on every step, as version 2's re-drawn card did, but by keying the element rather than redrawing; the toast sits above popovers and dialogs (`z-index: 100`, as version 2) and takes clicks, while the rest of its row lets clicks through; the code panel's token classes keep version 2's global names (`.t-kw`, `.t-ar`, `.t-cm`, `.t-tag`, `.t-tagtx`, `.t-al`) so tests and themes can address them; the Import dialog's textarea takes focus when it opens; a dialog body is keyboard-focusable so a tall dialog can be scrolled without a mouse; a side card's accessible name is "Go to Step N …" with its visible text, not a separate label.
- **One Esc, one thing.** Widgets that handle Esc themselves (the note editor, Find) stop the event so the page's Esc cascade does not also close the next thing.
- **`window.SWV` is not carried over.** Version 2 exposed its modules for debugging; version 3 has stores that React devtools can read, and every browser test drives the page through its controls. Parity row O13 is marked dropped.
- **AI replies go through Zod** (`zod` 4.6.7 in `apps/web`): the OpenAI-style answer (`choices[0].message.content`), the two error-body shapes and the artifact host's `{ text }` reply are the only shapes read, and only as strings. Anything else is "The provider sent no answer text". Later phases that add providers or structured replies (quiz, recap, review) extend these schemas rather than reading JSON by hand.
- **From the security branch, merged here:** every lookup table built from diagram words has no prototype (`wordTable`), so `constructor` or `__proto__` in a diagram is just a word; arrow pairing and reply matching are linear so a large pasted diagram cannot stall the page, and an arrow remembers at most 32 open blocks; a model request is sent with `redirect: 'error'`, `credentials: 'omit'` and `cache: 'no-store'`, so neither the question nor the key follows a redirect or lands in a cache; a provider's reply or error that repeats the key is shown, saved and logged with `[key hidden]`; changing the custom endpoint's address drops the key saved for the old address; a notes file cannot write `__proto__`; saved code that is not a string is ignored. The branch's scratch probe (`e2e/zz-probe.spec.ts` and a `window.__maxText` hook) was not kept; Mermaid's `maxTextSize` stays at its default 50 000, stated explicitly.
- **Dialog, panel and popover screens are axe-checked** in `e2e/a11y.spec.ts` with the WCAG 2.1 A and AA rules, in addition to the overview and the step bar. The checks are part of `npm run test:e2e`, so they run on every pull request.
- **Holes the finished security specs found, closed at the source:** (1) an `%%{init}%%` directive's `themeCSS` or `themeVariables` could make the page fetch from another site through `@import`, `url()` images, fills and `@font-face` in the SVG's own `<style>`; the sanitiser strips `@import` and every `url()` that is not a `#fragment` from style elements and attributes, and because Mermaid puts its drawing in the document before the sanitiser sees it, the same stripping is applied to the code's own `%%{init}%%` directives and front matter before Mermaid parses, so the page's policy is not the only thing in the way. (2) A 380 KB diagram of 20 000 nested `alt` blocks hung the page in Mermaid's parser; the viewer refuses code over Mermaid's 50 000-character limit before Mermaid sees it, with the same message Mermaid would give. (3) A share link that inflates to hundreds of megabytes hung the page; `inflate` reads the stream and stops at 4 MB, and the link falls back to the saved code with the usual notice. (4) A Markdown export escaped `[` but not `]`, so `[text](javascript:…)` in a step could still read as a link in a permissive reader; both brackets are escaped now. (5) Zod probes `Function('')` once to decide whether to compile schemas, which the page's policy reports as an eval attempt; it runs with `jitless: true`.
- **Draft security tests corrected rather than weakened:** the built page's policy `<meta>` is read with its HTML entities decoded; `<object>` and `<embed>` attacks point at an `.html` resource, because Chromium no longer fetches `.swf`; jsPDF's `/OpenAction [n 0 R /FitH null]` (open at page 1) is the one action a PDF may hold; an SVG's attack words may appear as text between tags, never as attributes; the key typed into the settings field is in that field's markup until the dialog closes, and nowhere else; `console.groq.com` in a provider's key-page address is not a console call; Mermaid 12.2 refuses `style A fill:url(…)` in a flowchart, so that attack is its own fixture and the flowchart with hostile labels and clicks still draws; the hostile flow is 5 500 px wide, so the hover helper picks an actor that is inside the viewport.

## Phase 11: structure review and threats (2026-10-31)

- **`@threat` is a step tag.** `%% @threat <high|medium|low> <short text>` belongs to the next arrow like `@unconfirmed`, and shows up as `step.threats` and `flow.threats`. A missing level or text is lint code `threat-format` and the line is dropped; text over 160 characters is `long-threat` and is still shown.
- **Seventh recorded difference from version 2** in `packages/core/src/golden.test.ts`: every step and flow has `threats`, and the "known tags" lint message names `@threat`.
- **Layer kinds fall back to participant names.** Most diagrams have no `@layer … kind=`, so the rules read the kind from a name such as `OrdersController` or `Payment Service`. Without this most rules could not run on most flows. A rule that still cannot run is listed as "Not checked" with the reason.
- **Rating points.** A high finding takes off 20, medium 10, low 5. One rule takes off at most twice its largest finding, so one habit repeated on many steps cannot sink the rating. The rating stops at 0. `@threat` lines never change it: they come from the diagram's author, and the rating comes only from the rules.
- **Confidence points.** Steps linked to code give up to 2, known layer kinds 1, flows reviewed in this browser up to 2 (2 flows give 1, 5 flows give 2). Unconfirmed details take off 1, or 2 when above 15% of the steps. A proposed design or a flow with no code links is always low. Otherwise 4 points or more is high and 2 or more is medium. The reasons are listed on screen.
- **`reply-missing` covers HTTP calls, outside calls and reads only.** The fast skill draws a reply only when a real value comes back, so a write with no reply arrow is normal and flagging it would be a false alarm.
- **A finding never repeats a secret.** It goes on screen and to the user's model, so query values and credential-like text are left out of what it says.
- **Threats column.** The step table's CSV gains a `Threats` column after `Unconfirmed`, and its Markdown "Also involved" cell gains `possible problem (level): text`. This is the one change to version 2's export shapes.
- **Explaining findings.** Plan section 5 sets no budget for this. It sends only the finding text (never the diagram code), for the 8 most serious findings at most, with 60 reply tokens per finding plus 20, so about 500 at most, in line with the day recap. The reply is words tied to finding numbers, validated with Zod and shown as plain text in its own block, so it cannot reach the rating.

- **Phases 6, 8 and 12 are skipped** (the user's decision, 2026-10-31): no models feature, no voice, and no demo tour, documents or release work from this plan. The review therefore explains findings through the Ask AI provider path of Phase 3, not a `@swv/ai` package.
- **The Ask AI provider path lives in `apps/web/src/shared/ai`** (`providers.ts`, `aiSettings.ts`, `cache.ts`, `complete.ts`, moved from `features/ask-ai`). The review needs it, features may not import each other, and code two features need belongs in `shared`. Ask AI keeps its own message building (`features/ask-ai/request.ts`) and its dialogs. `complete()` takes an optional `system` and `maxTokens`; without them it behaves exactly as before (Ask AI's system prompt, 220 reply tokens). A later feature that calls a model (quiz, recap) should call `complete()` from there.
- **`features/review/modelCall.ts` is the review's one way to a model.** It calls `complete()` with the review's system prompt and budget, reads the reply as JSON (a code fence around it is tolerated), validates it with the caller's Zod schema, and saves only a valid reply text in `swv:ai:cache`, under the provider and the whole request text, so a changed finding list is asked again and `Ask again` skips the saved answer. A reply the schema refuses is reported as `bad-reply` and not saved. No auto-switch and no consent step exist in this version, so the result carries no notices and the panel opens AI settings only when no model is set up.
- **What is sent is said on screen.** The explain panel states that only the text of the findings goes to the model, never the diagram or the key. That is this feature's answer to the privacy row of plan section 4.
- **The way in.** `ui.reviewOpen` opens the review dialog on its Structure tab and `ui.threatsOpen` on its Threats tab. The Overview card's "Review this flow" chip and the ⋯ menu's "Review this flow" item set `reviewOpen`. When Phase 7's tool registry lands on `main`, the menu item becomes one registry entry in the Analyze group that sets the same flag; the flag name stays.
- **Rule codes on screen.** Every finding and every rule in the dialog carries `data-rule` (rules also `data-status`: `passed`, `found` or `skipped`), so the browser tests name exactly what was found, passed or not checked instead of matching wording.
- **The demo flow's two findings stay.** `layers-skipped` on step 7 (the auth middleware reads the sessions table itself, although the flow has a Repository) and `outside-no-failure` on step 41 (the confirmation mail has no failure path drawn) are true of the demo's code, so they are not silenced. The browser test pins exactly these two, a rating of 80 and no threat; the clean flow of the core tests, with every layer and every step linked to code, gets 100 and nothing else.
- **`StepTags`** (taken from `feat/skills`): the nine step-level tag fields that `AnnotatedArrow` and `Step` share live in one `StepTags` type both extend, so jscpd does not count them as a clone.
- **A dialog gives the keyboard back to what opened it.** Radix returns focus to its own trigger, but every dialog here opens from a store flag, so focus used to fall to the page body. The shared `Dialog` remembers `document.activeElement` when it opens (in a layout effect, before Radix moves the focus inside) and focuses it again on close, when it is still in the page. This holds for the review and for every other dialog.
- **A finding names a step without repeating a secret.** A label that names a secret or token (`password=hunter2`) is said as "This call", and a password inside an address is dropped, in addition to query strings and credential-like text. The finding is what reaches the screen and the model.
- **Specs that changed with this phase, on purpose.** The CSV header in `e2e/export.spec.ts` gains `Threats`, the ⋯ menu list in `e2e/shell.spec.ts` gains "Review this flow". F16 and D28 block every script chunk except the entry; the lazy review chunk makes the bundler emit a `rolldown-runtime` chunk the entry imports, so that one is allowed too. Mermaid stays blocked and their assertions are unchanged.
## Phase 9: quiz (2026-10-31)

- **Phases 6 (models), 8 (voice) and 12 (demo tour, docs, release) are skipped**, by the user's decision on 2026-10-31. This branch carried the `@swv/ai` package from the skipped models phase (merged at `25a13b4`). The package stays, because the quiz writes questions and marks written answers through `callModel`, and its prompt helpers, Zod validation, token budgets, usage accounting and answer cache are what make that call safe. No models screen (usage bar, auto-switch settings, model list, cache view) was ever mounted in the app, so nothing was removed from `apps/web`; the package's exports meant for those screens stay as tested library code for whoever builds them.
- **Ask AI's settings are the only model list.** `@swv/ai` reads `swv:ai` (provider, keys, model override, custom link) on every load as model entries with fixed ids (`ask-ai-<preset>`) and never writes to it or copies a key anywhere else. The earlier migration that moved the keys out of `swv:ai` into `swv:ai:models` is gone: with the models phase skipped it would have emptied Ask AI's settings the first time the quiz opened. The chosen provider is the active model, nothing is a fallback, so auto-switch never reaches a second provider.
- **The quiz set-up screen is the privacy notice.** When a model is set up it names the host that receives the flow summary, the recent questions, the weak topics and the written answers, and says the key goes with them and nothing goes anywhere else. Pressing Start records the notice as read for those hosts (`grantConsent`), so `callModel` does not refuse the request; there is no second dialog. The built-in sample sends nothing.
- **Decisions 21 and 22 kept.** The stopwatch is the default time mode. With no model, the demo flow runs the built-in sample (five questions of each type at each level, 45 in all) and any other flow's Start button becomes "Open AI settings". With a model, the demo flow offers both sources.
- **A question is accepted only when its step exists and its answer and reason are backed by that step's text** (the step, its neighbours, its request and replies, the chapter and layer descriptions): every number, HTTP method and code name must appear there as written and at least 60% of the other words must match by stem. The question text and the wrong options of a multiple choice question are not checked, because they state nothing; they are only ever shown as text. Rejected questions are asked for again once, with the reasons, then the error names them.
- **Marking.** Multiple choice and the sample's written answers (keyword groups) are marked in the browser. A model quiz's written answers go to the model in one request after submit, at most 80 reply tokens each, labelled "AI marked" with "Mark as correct"; a user's mark is never overwritten by the model's and counts once in the weak points.
- **Temporary entry points.** A `Quiz` button in the top bar (hidden under 720 px) and a `Quiz` item in the `More` menu (shown under 1100 px), so every width has one. Phase 7's tool registry replaces both with one data entry; the flags stay `quizOpen` and `weakPointsOpen`.
- **Interface for other phases.** "Retry my mistakes" writes `sessionStorage['swv:quiz:retry'] = {"topics": string[], "flowId": string | null}` and then `setUi({ quizOpen: true })`; the set-up screen reads and clears the key, asks only those topics at every level and says when they came from another flow. Weak points live in IndexedDB under `swv:weak-points` through `shared/storage/weakPoints.ts` (`loadWeakPoints` is async); recent questions per flow under `swv:quiz:recent:<flowId>`.
- **Time off means no clock on the run screen**, and the result says "Not timed." The error after a failed retry gives the reasons of the last try; the first try's reasons go to the model in the retry's prompt.
- **Browser tests mock Groq with `page.route`** and answer with the built-in sample's questions, which the unit tests prove name real steps of the demo flow. The timer tests run on Playwright's clock, so a one-minute timer passes at once and no timeout is raised. PDFs are opened with `unpdf` (a dev dependency) to check their page count and text. The hostile-reply test runs with the page policy off, so React's plain-text rendering is what is proven.

## Phase 5: skills (2026-10-31)

- **`@threat` follows `feat/review`.** Both branches added `@threat` to `packages/core`; `feat/skills` now carries `feat/review`'s files byte for byte (`annotations.ts`, `types.ts`, `vocabulary.ts`, `flow.ts`, `golden.test.ts`, `threat.test.ts`): `%% @threat <high|medium|low> <short text>` above the arrow, lint codes `threat-format` and `long-threat` (text over 160 characters), `parseThreat`, `Flow.threats` with each threat's step index, `THREAT_LEVELS` and `THREAT_MAX_CHARS`. Two files then differ: `index.ts` by the validator's exports, and `types.ts` by one refactor jscpd forced (below). The later merge of `feat/review` touches only those two places.
- **`StepTags` in `types.ts`.** With `threats: Threat[]` added, `AnnotatedArrow` and `Step` repeated nine identical fields, which jscpd (configured to fail on any clone) reports on both `feat/skills` and `feat/review`. The nine fields now live once in `StepTags`, which both interfaces extend; nothing else changed. `feat/review` needs the same change before its gate passes: cherry-pick this hunk, or take `feat/skills`' `types.ts` when the merge conflicts there.
- **One validator, shipped in both skills.** `packages/core/src/validate.ts` is the single implementation (plan decision 25). `tools/build-skills` bundles it with rolldown into `scripts/validate.mjs` (Node only, no imports), the same bytes for `detailed-seq-diagram`, which must run it, and for `seq-diagram`, which runs it only when asked to check a pasted diagram. `validate.py` is gone; `packages/core/fixtures/validate-python.golden.json` keeps its verdicts, and `validate.test.ts` proves the TypeScript validator agrees with them.
- **No Python copy of the validator.** Whether Node runs in the Claude app's skill sandbox could not be proven from this machine (it needs the user's account). Anthropic's documentation of the API code-execution container lists Python 3.11 only; the claude.ai help article says Claude can "write and run code (for example Python or Javascript)" there and reach npm when network access is on, which implies Node but says nothing about skills. A generated Python copy would be a second parser of about 50 KB that cannot be derived from the TypeScript source, so it would drift, which is the very risk the plan names. So: `seq-diagram` never runs the validator (the viewer checks on paste); `detailed-seq-diagram` lists what to check by hand when `node` is missing; and the Claude app install (plan 7.7 step 2, Finishing step 3) is where a real run must confirm Node. If it is not there, the fallback is a Python copy tested against the same fixtures.
- **The old `skill/` and `skill-kit/` folders are removed.** The sources are `skills/`; `npm run build:skills` generates the kit (`SKILL-SETUP-GUIDE.md`, `install.mjs`, both skill folders, one zip per skill and `sequence-walkthrough-skill-kit.zip`) into `tools/build-skills/dist/`. `apps/web/vite-plugins/skillKit.ts` reads that build output, and version 2's `build.py`, which read the old folders, went in Phase 4.
- **The sample projects prove the rules in code, not the model.** `skills/fixtures/<sample>/expected.json` holds the facts of each sample with `[file, text]` evidence, and `expected.mmd` the diagram `seq-diagram` should write. `tools/build-skills/src/fixtures.test.ts` checks that the evidence is really in the code; that the diagram passes the validator with every link resolving; that its layers, request, statuses, messages, fields, names and links match `expected.json`; that every `@layer` names a folder or file on the path that a token of `layer-naming.md` maps; and that nine ways to drift (a wrong status, path or field, a link off the path or to a missing line, middleware as a side part, a layer drawn twice, no `autonumber`, a split label) are caught. Whether a model writes such a diagram is shown only by a real run (below), and `docs/feature-tests.md` says so row by row.
- **`layer-naming.md` gained three tokens** the samples needed: Django's app `middleware.py`, Next.js `lib/` as Service, and a guard exported by another feature (`auth/require-session.ts`) as Middleware in feature folders.
- **Reading evidence comes from the transcript.** `tools/build-skills/src/run-evidence.ts` reads a Claude Code transcript (`.jsonl`) and lists the files a run opened (the Read tool, or `cat`, `sed`, `head`, `tail` in a shell), in order, with repeats, whether the README came first, files outside the project and the wall-clock time; the CLI is `node tools/build-skills/src/run-evidence-cli.ts <transcript> <project>`. The previous agent's unfinished transcript tool was never saved, so this one was written from scratch and kept small.
- **Measured run on `examples/demo-store`** (2026-10-31; one sub agent, model claude-fable-5-1, given exactly the built `seq-diagram/SKILL.md` plus the one-line request; its reply is kept unchanged in `docs/runs/demo-store-seq-diagram.md`): wall clock **354.6 s** from the first to the last transcript event (the Agent tool reported 354.7 s), 8 tool calls, **31 files opened, none twice, README first**, 29 of them code, nothing outside the project. It also opened `flows/place-order.mmd`, the demo's own reference diagram, which the reading rule "if a README or reference file covers that folder or file, read it first" allows. Diagram: **58 steps, 20 layers, 5 chapters, 17,047 bytes** of code. Validator with `--root examples/demo-store`: **0 errors, 0 warnings, 3 hints** (`step-outcome`), every code link resolving (54 steps linked). Reading took 40 s (09:54:53 to 09:55:27 UTC); the remaining five minutes went into writing the 17 KB reply. The plan's goal of 60 to 75 seconds is for a small flow of about 8 KB; the demo store crosses 20 layers with Redis, an event bus, a queue and a worker, so this run does not measure that goal, and no CI budget depends on it.
- **Budgets measured in CI** (`tools/check-budgets`): `seq-diagram/SKILL.md` 7,990 bytes of 8,192; `detailed-seq-diagram/SKILL.md` 13,990 of 15,360; both descriptions under 1,024 characters. The build itself stops on a description over 1,024 characters, one without its own trigger phrases, or one carrying the other skill's (plan 7.5).
- **`seq-diagram` ships no examples.** Its text tells the model to read nothing in the skill's folders, so an example would never be opened; `detailed-seq-diagram` ships two, checked by the validator at the strict bar on every build.
- **knip on the build machine runs with `KNIP_DISABLE_RAW_TRANSFER=1`.** knip parses with oxc-parser's raw transfer, which allocates one large `ArrayBuffer` per parse; with under 1 GB of memory free that allocation failed (`RangeError: Array buffer allocation failed`) on every run, including the gate's. The variable is knip's own switch to its ordinary parser and changes nothing in what it reports; CI on Ubuntu runs plain `knip`. It was set only on the local gate command, not in `package.json`.
- **`playwright.config.ts` reads `SWV_E2E_PORT`**, the same two lines every other phase branch has. `main` still hardcodes 4173 and reuses any server already on it, so the first gate on this branch tested another worktree's preview server (its page showed the Phase 3 viewer, not this branch's app). With the variable the gate serves this worktree on its own port.

## Phase 7: new design (2026-10-31)

- **Scope cut by the user on 2026-10-31.** Phases 6 (models: usage bar, auto-switch, cache, model list), 8 (voice) and 12 (demo tour, docs, release) are skipped. The dock holds Play, speed, the Flow Rail and the chapters, with no voice button; the Settings group holds the page theme, the Ask AI provider settings and keys, and stored data, with no usage bar or cache. The `besidePlay` and `besideAsk` slots the dock and the step card kept for them are gone. The `data-tour` names stay on the header, each tool group, the dock and the Flow Rail: they are cheap and document the structure.
- **A tool is one data entry** in `apps/web/src/app/tools/registry.ts`: `{ id, group, label, icon, tour, count?, hint? }` plus either `panel` (a lazy component shown in the overlay) or `run` (an action, usually `setUi({ someOpen: true })`), and optionally `host` (a lazy dialog mounted once for the page). The header menus, the phone's ⋯ menu, the overlay's side list and the tour all read the list, so Quiz, day recap, weak points, Structure review and threats each add a line and nothing else. The `id` is also the value of `ui.overlayTool`, which is how another feature opens a tool without importing it.
- **The Export menu is registry data too.** Its seventeen items (PDF, the PNG scales, SVG, step image, code, step table, Markdown, the mermaid.live and viewer links, provider and key, the skill, paste and open a file) are `run` entries of the `export` group, each with a `section` heading and, for the PNG scales, a shared `row`; `ToolMenuItems` draws headings, compact rows and items from that, so the quiz exports of Phase 9 are two more lines. Order, labels, hints and headings are version 2's (parity F19).
- **The Insight panel became the overlay's panes.** `I` opens Analyze → Layers; Analyze holds Layers, Endpoints, Errors, Data and Side parts, and Glossary sits in Learn as plan 8.5 says. Each pane keeps `data-testid="insight"` so the old-data, security and Ask AI specs assert the same things; only the way they open the pane changed (`openPanel` in `e2e/helpers.ts`).
- **The Flow Rail replaces the progress bar** and keeps its test ids. It is a `role="slider"` (aria-valuenow is the step, aria-valuetext reads the step, chapter, label and marks) whose fill is CSS from `--cur`, so a step change costs no render. Markers: errors on the line, side parts below it, threats and bookmarks above it. W6 asserts the slider's value instead of counting `[data-done]` cells.
- **Threat markers read `step.threats` when the field exists.** Phase 11 adds `%% @threat` to core; `railModel.threatsOf` reads the optional field, so the demo shows no threat marker until then, and `design.spec.ts` asserts that.
- **The overlay's visible title is its accessible name.** `OverlayTitle` wraps the visible heading with `asChild`, so a screen reader hears "Layers" once, not an sr-only copy and then the heading. Menus are named by their `aria-label`, not by their trigger (Radix points `aria-labelledby` at the trigger, which here is the short group name).
- **"Only this layer" in the Layers pane closes the overlay** so the spotlight it sets can be seen; "Show all" is on the canvas notice, as for the path filter.
- **The overlay is a modal Radix dialog.** Everything behind it is inert, so a test that changes a setting inside it (the diagram theme) closes it before using the page: `setDiagramTheme`, `openPanel`, `closeOverlay` in `e2e/helpers.ts`. The opener is remembered by the menu item (`overlayFocus.ts`) and gets the focus back; opened by `I`, the diagram does.
- **The first load dropped from 199.6 KB to 177.4 KB gzipped** (budget 200 KB, enforced by `tools/check-budgets`): Ask AI with Zod and the two help dialogs are downloaded on first use (`shared/ui/Deferred.tsx` mounts them when their flag first turns on and keeps them mounted), and DOMPurify travels in the Mermaid chunk, since it only ever sanitises Mermaid's output. The code panel and the table stay in the first load: a key opens them and their rows are counted at once, by the specs and by anyone who presses `T`.
- **The diagram theme follows the page by default** (`settings.themeAuto`: Redux Color on light pages, Redux Dark Color on dark ones). A theme saved by version 2, picked in Settings or named by an imported diagram or mermaid.live link is the user's choice and turns it off (`flowStore.loadCode`).
- **Side cards are named by their text.** The `aria-label="Go to step N"` the design branch added failed axe's label-content-name-mismatch; the sr-only "Go to" prefix already names them.
- **Four lint errors in the merged Phase 3 specs were fixed here** (an `import()` type, a literal BOM in a regex, an `any` from `Object.fromEntries`, an `as` on an array element) because the gate runs `npm run lint` over `e2e/`.


- **Dark diagrams are read as dark.** Mermaid's dark themes give `background: "#333"`, and the check only read six-digit colours, so every dark theme counted as light: a pale chapter band over the arrows and dark dots on a dark canvas. The check now reads both forms, at the source rather than per theme.
- **The dot grid keeps its spacing.** Dots double their spacing when zoomed out, so a large flow at fit does not turn the canvas into grey fog.
- **Fit stays clear of the floating tools.** The first view and Fit keep 64 px at each side (24 px on a phone) and start below the Code button, so no layer sits under a tool. The diagram is slightly smaller at fit as a result.
- **A step link closes the overlay.** The jump is there to show the diagram. Opened again, the overlay marks the current step.

- **The lockfile comes from a from-scratch resolve.** `npm install` on Windows prunes the top-level `@emnapi/core` and `@emnapi/runtime` entries that `npm ci` needs on Linux, so it must not be run over this lockfile on Windows; use `npm ci` to sync.
- **The chapter lock moved to the dock, and the fold tab keeps it.** "Hide the step bar" puts the step cards away; the dock stays, so Play and the Flow Rail are still there.
- **The overlay is modal, so it closes first in the Esc order.** Insight is no longer a step of its own between hide mode and the code panel.
