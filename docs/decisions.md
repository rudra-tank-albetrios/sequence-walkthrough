# Decisions

Decisions the plan (`docs/IMPLEMENTATION-PLAN.md`) does not already make, one or two lines each, newest last.

## Phase 1: foundation (2026-10-30)

- **TypeScript 5.9, not 7.** TypeScript 7 (the native compiler) is current on npm, but typescript-eslint supports only versions below 6.1. The 5.9 line is pinned until the lint tooling catches up; Dependabot will propose the bump and CI will tell us when it works.
- **ESLint 10 without eslint-plugin-jsx-a11y.** The a11y plugin does not support ESLint 10. Accessibility is checked where it matters, on the rendered page, with axe-core in the Playwright tests.
- **Workspace packages export their TypeScript source.** `@swv/core` and `@swv/ai` point `exports` at `src/index.ts`. Vite bundles them into the app, Vitest reads them directly, and Node 24 runs the tools' `.ts` files without a build step. `erasableSyntaxOnly` is on so Node's type stripping always works. Nothing in `packages/` needs to be compiled before use.
- **Package scope `@swv`.** Short, and it matches the `swv:` prefix the viewer has always used for browser storage.
- **Content Security Policy as a `<meta>` tag.** GitHub Pages cannot set response headers. The tag is added only to production builds, because the Vite dev server and React refresh need an inline script while developing.
- **Python stays only in the deploy workflow** until Phase 4 switches hosting to the new app. `npm run verify` has no Python step.
- **Playwright runs a phone project (Pixel 7)** in addition to Chromium, Firefox and WebKit, because the plan requires a phone layout.
- **Gitleaks through the official GitHub Action.** It is free for repositories owned by a user account, which this one is.
- **Repository settings:** squash and rebase merges are turned off so every merge is a merge commit (plan section 1, rule 7); branches are deleted on merge; GitHub secret scanning, push protection, Dependabot security updates and private vulnerability reporting are turned on. All are free on a public repository.
- **Firefox runs in CI only on the build machine.** Playwright's Firefox build does not start on the Windows machine used for the build ("side-by-side configuration is incorrect", a missing system runtime), and installing system components is out of scope. CI on Ubuntu runs all four browser projects; locally `SWV_E2E_PROJECTS=chromium,webkit,phone npm run verify` runs the rest. The variable is ignored in CI.
- **A ruleset ("Protect main") instead of classic branch protection.** It requires a pull request, an up-to-date branch, merge commits only, and the checks `verify`, `gitleaks`, `CodeQL (javascript-typescript)` and `CodeQL (actions)` (the CodeQL job is a matrix, so each language reports its own check). It also blocks force pushes and deletion. No required review, since GitHub does not let an account approve its own pull request. Renaming a job or the matrix changes the check names and must be mirrored in the ruleset.

## Phase 2: core package and demo store (2026-10-30)

- **Golden files come from the version 2 parser running in a real browser.** `tools/golden` opens the version 2 page in Playwright, feeds Mermaid 12.2.0 to it from Node (a headless page opened from disk cannot reach the CDN reliably) and records `Annotations.parse`, Mermaid's own view of the arrows and `buildFlow` for every fixture in `packages/core/fixtures`. It is a migration tool, not part of `npm run verify`. Phase 4 removed the tool; its section below says how to record a new golden.
- **Version 3 reads the Mermaid sequence syntax itself** (`packages/core/src/sequence.ts`) instead of asking Mermaid for its parsed messages. The browser still renders with Mermaid, but the parser now runs in Node, in the skills' validator and in tests without a DOM, and arrows map to source lines directly. The goldens prove it reads participants, arrows, arrow styles and block nesting exactly as Mermaid 12.2.0 does for every fixture.
- **Six recorded differences from version 2**, each named in `packages/core/src/golden.test.ts`: (1) Mermaid's internal entity placeholders (`ﬂ°°59¶ß`) no longer leak into labels; `#59;` decodes to `;`. (2) A side part used twice on one step lists that step once. (3) `endings` are step indexes, not copies of step objects. (4) When Mermaid refuses the code, version 3 still reads participants and blocks and reports the exact line (`flow.syntax`), where version 2 fell back to a regex read. (5) The eight backend layer kinds the plan names (app, router, validator, controller, serializer, repository, eventbus, cron) are recognised, plus `dto`; version 2 on `main` knew ten kinds. (6) `main` is always present.
- **A bare `;` splits a line into statements**, because that is what Mermaid's lexer does (`A->>B: hi; B-->>A: ok` draws two arrows). Both scanners split the same way, so arrows and annotations stay paired. Text after a `;` that is not a statement is reported as `semicolon`.
- **Mermaid-incompatible lines are reported by the parser** as `flow.syntax` with the codes `semicolon`, `no-colon`, `unknown-line`, `block` and `keyword-alias` (the codes `validate.py` used), kept apart from the viewer's `flow.lint` so the lint shape stays identical to version 2.
- **Half-arrow styles (`-/`, `-|`, `-\`)** are parsed as arrows but typed as open arrows; Mermaid's exact LINETYPE numbers for them were not verified and no fixture uses them.
- **Demo flow error replies are drawn from App to API Client** (`APP-->>API: 401 Unauthorized`), not from the middleware or validator that produced them, so each reply pairs with the main request and shows as one of its endings. The step text says which layer produced the response.
- **The demo's in-memory database is described with the SQL it stands in for** in `@payload.sql` lines, each marked "an in-memory table, doing the job of", so the Data tab shows the tables touched without claiming the demo runs SQL.
- **`process.stdout.write` stays allowed.** The raw-HTML lint rule now bans only `document.write`/`writeln`, not every `.write(` call. It requires a pull request, an up-to-date branch, merge commits only, and the checks `verify`, `gitleaks`, `CodeQL (javascript-typescript)` and `CodeQL (actions)` (the CodeQL job is a matrix, so each language reports its own check). It also blocks force pushes and deletion. No required review, since GitHub does not let an account approve its own pull request. Renaming a job or the matrix changes the check names and must be mirrored in the ruleset.

## Phase 3: React viewer (2026-10-31)

- **The demo flow is the default diagram** (`examples/demo-store/flows/place-order.mmd`, imported at build time) and the "Load example" code, replacing the payment example version 2 shipped. The plan's section 8.12 asks for this; doing it now keeps one default for the rest of the build.
- **One parser for the viewer.** The page parses with `@swv/core` and uses Mermaid only to draw. Arrow N in the code is drawn arrow N, so the SVG mapping is by position, as in version 2, and a count mismatch shows a toast instead of guessing.
- **Mermaid output goes through DOMPurify** before it reaches the page, in the one component (`features/viewer/DiagramSvg.tsx`) the lint rule allows. The `name` attribute Mermaid puts on participants and the `<style>` element with the theme are kept; scripts, event handlers and links are not.
- **Content Security Policy:** `connect-src 'self' https: http://localhost:* http://127.0.0.1:*`, because Ask AI calls whichever model URL the user chose and Ollama runs on localhost over http. Scripts stay `'self'`.
- **Colours use `light-dark()`**, so every token is declared once and the theme choice only switches `color-scheme`. The user-interface theme follows the system, as in version 2; the diagram theme is the setting the user picks.
- **Feature folders own their screens; shared state lives in Zustand stores under `shared/state`.** Features talk through the stores (`ui` flags such as `askOpen`, `importOpen`) and never import each other; `dependency-cruiser` checks it. The one hand-over outside the stores is the right-click menu's "Ask AI: what is X?", which leaves the question in `sessionStorage` under `swv:ask:prefill`.
- **The keyboard map is the shell's** (`app/useGlobalKeys.ts`), including the Esc cascade in version 2's order; widgets handle only their local keys.
- **Version 2 behaviours kept as they really were, not as the README said:** `Home` goes to step 1 (the overview is reached with Esc or at load), and the Claude provider has no consent step of its own in the page (the host's prompt is the consent).

## Phase 4: cutover (2026-10-31)

- **The website is built from `apps/web/dist` by Node.** `deploy-pages.yml` has two jobs: `build`, read-only with no npm cache, so no dependency code runs next to a deploy token, and `deploy`, with only `pages: write` and `id-token: write`. `actions/configure-pages` went with Python: it only reads settings the relative `base: './'` does not need, and `deploy-pages` does not depend on it. Same URL, because the repository name and the Pages source did not change.
- **Version 2's code stays in git history, and `tools/golden` is removed.** Both tools ran the version 2 page, so they cannot outlive it, and carrying code that fetches old files out of git would be more to maintain than the recipe below. The goldens in `packages/core/fixtures` are checked in and `golden.test.ts` keeps reading them.
  - `398d08e` holds the last version 2 app (`src/`, `build.py`); both are byte-identical from there to the commit before this cutover.
  - `debfb9b` (the merge of Phase 2) holds that app and the recorder. To record a golden for a new fixture: `git worktree add ../swv-v2 debfb9b`, then in it `npm ci`, `python build.py`, copy the `.mmd` into `packages/core/fixtures`, `node tools/golden/src/index.ts <name>`, and copy the `.golden.json` back.
  - `8ea0b62` also holds `tools/golden/src/compare.ts`, the old-against-new screenshot tool.
- **`dist/` and `dist-claude/` were never tracked**, so the only clean-up was the ignore files.
- **The one-file build is two pages.** `npm run build:single -w @swv/web` (`vite build --mode single`, also part of `npm run build`) writes to `apps/web/dist-single/`. Version 2 had the same pair: `sequence-walkthrough.html` is a whole document to open from disk, as version 2's `dist/index.html` was, and `sequence-viewer.html` is that page without doctype, `html`, `head`, `body` or policy, as `dist-claude/` was, because the Artifact tool wraps a page in its own skeleton. The build stops if any file is left outside the page.
- **The one-file page's policy allows one script, by hash.** `script-src 'self'` would block the inlined script, and `'unsafe-inline'` would let any injected script run, so `vite-plugins/oneFilePage.ts` computes the SHA-256 of the script after inlining and allows only that. The rest is stricter than the website's: `default-src 'none'`, and images and fonts only from `data:` and `blob:`. `connect-src` stays open to `https:` and localhost because Ask AI calls the model URL the user chose. `style-src 'unsafe-inline'` stays because Mermaid writes styles into its SVG. The website's policy is unchanged, and `e2e/hosted.spec.ts` fails if it moves.
- **The artifact page has no policy of its own, because it must not have one.** The host sets the policy, and its runtime loads a capability's module when `claude.use()` is called (runtime contract 0.2.94), so a page policy allowing only our hash could block the Claude provider and the save dialog. For the same reason that file is never put on the website: with no policy, on the site's origin, it would sit next to people's stored API keys.
- **People get the one-file viewer from `sequence-walkthrough-one-file.zip`, published next to the website**: `https://rudra-tank-albetrios.github.io/sequence-walkthrough/sequence-walkthrough-one-file.zip`. It holds both pages and a short `README.txt`. A zip is inert on the site's origin, is about a third of the size, and needs no release to exist. `npm run build` copies it next to the site, so GitHub Pages and Netlify publish the same thing. The guide dialog on the website links to it. Phase 12 can also attach it to the `v3.0.0` release.
- **Inside the one-file page, nothing fetches.** The skill kit is carried in the page as text (`__SKILL_KIT__`, only in that build), as version 2 embedded it, and export code reads the fonts from their `data:` URLs, so `connect-src` does not need `data:`.
- **`sequence-walkthrough.zip` stays on the website and now holds the skill kit.** Version 2 published it and links to it exist, but `tools/build-skills` no longer makes a skill of that name, so `skillKit.ts` publishes the kit under both addresses.
- **The Claude provider handles the runtime's real answers.** `claude.use('sample')` resolves `null` when a view cannot run it, and a refusal is a plain `{ code, message }`, so the panel says so in words. `request.ts` is `main`'s with only this added back on top, because `request.test.ts` holds this behaviour to account and `main`'s file alone fails it. The artifact tests run against a stub of runtime contract 0.2.94, because a real host cannot be driven from a test.
- **Flowchart, class and state labels.** The one-file test for other diagram types found that DOMPurify removed `<foreignObject>`, where Mermaid puts those labels, so they drew with no text on the website too. Allowing that element let hostile markup reach the page and failed `security.spec.ts`, so `features/viewer/mermaid.ts` sets `htmlLabels: false` and Mermaid draws those labels as SVG text, with `<foreignObject>` still refused.
- **The link preview tags came back.** Version 2's page had `og:type`, `og:title` and `og:description`, and the new `index.html` had lost them. They are plain text with no address in them, so both builds carry them.
- **Prettier has never checked a `src` folder, and this phase does not change that yet.** `.prettierignore`'s `src/` line, meant for the version 2 app, matched every `src` folder at any depth. Removing it would reformat over 100 files and conflict with every open build branch, so it is now an explicit `**/src/` line with a comment. When no build branch is open, delete that line and run `npm run format` in one commit.
- **The merge with `main` (PR 8 and the skills).** `main` wins on viewer and feature code, and the cutover wins on removing version 2. `skillKit.ts` is `main`'s, with `readSkillKit` exported so the one-file build can carry the same kit (`__SKILL_KIT__`, in `vite.config.ts`). `zipEntries` moved to `oneFilePage.ts`, its only remaining user.
- **The one-file page escapes NUL bytes.** The bundler writes a `\0` in a string as a raw byte. The HTML parser reads that as U+FFFD, so the browser's hash of the inlined script differed from the policy's and the page did not start. `npm run check` opens only the website, so it passed anyway; `e2e/one-file.spec.ts` found it. `oneFilePage.ts` now writes the byte as `\u0000` before hashing.
- **Known failures after the merge, outside `npm run check`:** `e2e/hosted.spec.ts` on `sequence-walkthrough.zip` and `e2e/one-file.spec.ts` on other diagram types (no label text). Both are the open points above.

## Phase 5: skills (2026-10-31)

- **`@threat` follows `feat/review`.** Both branches added `@threat` to `packages/core`; `feat/skills` now carries `feat/review`'s files byte for byte (`annotations.ts`, `types.ts`, `vocabulary.ts`, `flow.ts`, `golden.test.ts`, `threat.test.ts`): `%% @threat <high|medium|low> <short text>` above the arrow, lint codes `threat-format` and `long-threat` (text over 160 characters), `parseThreat`, `Flow.threats` with each threat's step index, `THREAT_LEVELS` and `THREAT_MAX_CHARS`. Two files then differ: `index.ts` by the validator's exports, and `types.ts` by one refactor jscpd forced (below). The later merge of `feat/review` touches only those two places.
- **`StepTags` in `types.ts`.** With `threats: Threat[]` added, `AnnotatedArrow` and `Step` repeated nine identical fields, which jscpd (configured to fail on any clone) reports on both `feat/skills` and `feat/review`. The nine fields now live once in `StepTags`, which both interfaces extend; nothing else changed. `feat/review` needs the same change before its gate passes: cherry-pick this hunk, or take `feat/skills`' `types.ts` when the merge conflicts there.
- **One validator, shipped in both skills.** `packages/core/src/validate.ts` is the single implementation (plan decision 25). `tools/build-skills` bundles it with rolldown into `scripts/validate.mjs` (Node only, no imports), the same bytes for `detailed-seq-diagram`, which must run it, and for `seq-diagram`, which runs it only when asked to check a pasted diagram. `validate.py` is gone; `packages/core/fixtures/validate-python.golden.json` keeps its verdicts, and `validate.test.ts` proves the TypeScript validator agrees with them.
- **No Python copy of the validator.** Whether Node runs in the Claude app's skill sandbox could not be proven from this machine (it needs the user's account). Anthropic's documentation of the API code-execution container lists Python 3.11 only; the claude.ai help article says Claude can "write and run code (for example Python or Javascript)" there and reach npm when network access is on, which implies Node but says nothing about skills. A generated Python copy would be a second parser of about 50 KB that cannot be derived from the TypeScript source, so it would drift, which is the very risk the plan names. So: `seq-diagram` never runs the validator (the viewer checks on paste); `detailed-seq-diagram` lists what to check by hand when `node` is missing; and the Claude app install (plan 7.7 step 2, Finishing step 3) is where a real run must confirm Node. If it is not there, the fallback is a Python copy tested against the same fixtures.
- **The old `skill/` and `skill-kit/` folders are removed.** The sources are `skills/`; `npm run build:skills` generates the kit (`SKILL-SETUP-GUIDE.md`, `install.mjs`, both skill folders, one zip per skill and `sequence-walkthrough-skill-kit.zip`) into `tools/build-skills/dist/`. `apps/web/vite-plugins/skillKit.ts` reads that build output, and version 2's `build.py`, which read the old folders, went in Phase 4.
- **The sample projects prove the rules in code, not the model.** `skills/fixtures/<sample>/expected.json` holds the facts of each sample with `[file, text]` evidence, and `expected.mmd` the diagram `seq-diagram` should write. `tools/build-skills/src/fixtures.test.ts` checks that the evidence is really in the code; that the diagram passes the validator with every link resolving; that its layers, request, statuses, messages, fields, names and links match `expected.json`; that every `@layer` names a folder or file on the path that a token of `layer-naming.md` maps; and that nine ways to drift (a wrong status, path or field, a link off the path or to a missing line, middleware as a side part, a layer drawn twice, no `autonumber`, a split label) are caught. Whether a model writes such a diagram is shown only by a real run (below), and `docs/feature-tests.md` says so row by row.
- **`layer-naming.md` gained three tokens** the samples needed: Django's app `middleware.py`, Next.js `lib/` as Service, and a guard exported by another feature (`auth/require-session.ts`) as Middleware in feature folders.
- **Reading evidence comes from the transcript.** `tools/build-skills/src/run-evidence.ts` reads a Claude Code transcript (`.jsonl`) and lists the files a run opened (the Read tool, or `cat`, `sed`, `head`, `tail` in a shell), in order, with repeats, whether the README came first, files outside the project and the wall-clock time; the CLI is `node tools/build-skills/src/run-evidence-cli.ts <transcript> <project>`. The previous agent's unfinished transcript tool was never saved, so this one was written from scratch and kept small.
- **Measured run on `examples/demo-store`** (2026-10-31; one sub agent, model claude-fable-5-1, given exactly the built `seq-diagram/SKILL.md` plus the one-line request; its reply is kept unchanged in `docs/runs/demo-store-seq-diagram.md`): wall clock **354.6 s** from the first to the last transcript event (the Agent tool reported 354.7 s), 8 tool calls, **31 files opened, none twice, README first**, 29 of them code, nothing outside the project. It also opened `flows/place-order.mmd`, the demo's own reference diagram, which the reading rule "if a README or reference file covers that folder or file, read it first" allows. Diagram: **58 steps, 20 layers, 5 chapters, 17,047 bytes** of code. Validator with `--root examples/demo-store`: **0 errors, 0 warnings, 3 hints** (`step-outcome`), every code link resolving (54 steps linked). Reading took 40 s (09:54:53 to 09:55:27 UTC); the remaining five minutes went into writing the 17 KB reply. The plan's goal of 60 to 75 seconds is for a small flow of about 8 KB; the demo store crosses 20 layers with Redis, an event bus, a queue and a worker, so this run does not measure that goal, and no CI budget depends on it.
- **Budgets measured in CI** (`tools/check-budgets`): `seq-diagram/SKILL.md` 7,990 bytes of 8,192; `detailed-seq-diagram/SKILL.md` 13,990 of 15,360; both descriptions under 1,024 characters. The build itself stops on a description over 1,024 characters, one without its own trigger phrases, or one carrying the other skill's (plan 7.5).
- **`seq-diagram` ships no examples.** Its text tells the model to read nothing in the skill's folders, so an example would never be opened; `detailed-seq-diagram` ships two, checked by the validator at the strict bar on every build.
- **knip on the build machine runs with `KNIP_DISABLE_RAW_TRANSFER=1`.** knip parses with oxc-parser's raw transfer, which allocates one large `ArrayBuffer` per parse; with under 1 GB of memory free that allocation failed (`RangeError: Array buffer allocation failed`) on every run, including the gate's. The variable is knip's own switch to its ordinary parser and changes nothing in what it reports; CI on Ubuntu runs plain `knip`. It was set only on the local gate command, not in `package.json`.
- **`playwright.config.ts` reads `SWV_E2E_PORT`**, the same two lines every other phase branch has. `main` still hardcodes 4173 and reuses any server already on it, so the first gate on this branch tested another worktree's preview server (its page showed the Phase 3 viewer, not this branch's app). With the variable the gate serves this worktree on its own port.

## PR 8

- Code over 50,000 characters is refused before anything reads it. `setCode` keeps the last good flow and only stores the text; the drawing step shows Mermaid's message. Reading and showing 40,000 steps first stopped the page for 7 to 11 seconds.
- The skill kit is read from `tools/build-skills/dist`, and built on demand when missing. The kit's name is unchanged, so links keep working.
- On WebKit the eval and Function constructor attacks stay blocked even with the policy lifted by the test tool, so "with the policy off" there only proves they stay stopped. Chromium and Firefox run the real control.
- `Viewer.tsx` finds the word under a double-click from the label's on-screen box. On WebKit this gives the same point as `getScreenCTM`; the D22 failure was Playwright's `boundingBox`, which is off for SVG text there, so the test now reads the box from the page.

- GitHub Actions no longer gate merges (user decision, 2026-10-31). `ci.yml` and `codeql.yml` are gone and `Protect main` requires no status checks; only `deploy-pages.yml` remains. `npm run check` (`scripts/check-basic.ts`) runs types, lint, unit tests, the build and budgets, then opens the built site in one browser, and must pass locally before a merge. `npm run verify` stays for full runs by hand. This also ends automatic CodeQL and Gitleaks scans on pull requests.
