# Decisions

Decisions the plan (`docs/IMPLEMENTATION-PLAN.md`) does not already make, one or two lines each, newest last.

## Phase 1: foundation (2026-10-30)

- **TypeScript 5.9, not 7.** TypeScript 7 (the native compiler) is current on npm, but typescript-eslint supports only versions below 6.1. The 5.9 line is pinned until the lint tooling catches up; Dependabot will propose the bump and CI will tell us when it works.
- **ESLint 10 without eslint-plugin-jsx-a11y.** The a11y plugin does not support ESLint 10. Accessibility is checked where it matters, on the rendered page, with axe-core in the Playwright tests.
- **Workspace packages export their TypeScript source.** `@swv/core` and `@swv/ai` point `exports` at `src/index.ts`. Vite bundles them into the app, Vitest reads them directly, and Node 24 runs the tools' `.ts` files without a build step. `erasableSyntaxOnly` is on so Node's type stripping always works. Nothing in `packages/` needs to be compiled before use.
- **Package scope `@swv`.** Short, and it matches the `swv:` prefix the viewer has always used for browser storage.
- **Content Security Policy as a `<meta>` tag.** GitHub Pages cannot set response headers. The tag is added only to production builds, because the Vite dev server and React refresh need an inline script while developing.
- **Python stays only in the deploy workflow** until Phase 4 switches hosting to the new app. `npm run verify` has no Python step.
- **Playwright runs a phone project (Pixel 7)** in addition to Chromium, Firefox and WebKit, because the plan requires a phone layout.
- **Gitleaks through the official GitHub Action.** It is free for repositories owned by a user account, which this one is.
- **Repository settings:** squash and rebase merges are turned off so every merge is a merge commit (plan section 1, rule 7); branches are deleted on merge; GitHub secret scanning, push protection, Dependabot security updates and private vulnerability reporting are turned on. All are free on a public repository.
- **Firefox runs in CI only on the build machine.** Playwright's Firefox build does not start on the Windows machine used for the build ("side-by-side configuration is incorrect", a missing system runtime), and installing system components is out of scope. CI on Ubuntu runs all four browser projects; locally `SWV_E2E_PROJECTS=chromium,webkit,phone npm run verify` runs the rest. The variable is ignored in CI.
- **A ruleset ("Protect main") instead of classic branch protection.** It requires a pull request, an up-to-date branch, merge commits only, and the checks `verify`, `gitleaks`, `CodeQL (javascript-typescript)` and `CodeQL (actions)` (the CodeQL job is a matrix, so each language reports its own check). It also blocks force pushes and deletion. No required review, since GitHub does not let an account approve its own pull request. Renaming a job or the matrix changes the check names and must be mirrored in the ruleset.

## Phase 2: core package and demo store (2026-10-30)

- **Golden files come from the version 2 parser running in a real browser.** `tools/golden` opens the version 2 page in Playwright, feeds Mermaid 12.2.0 to it from Node (a headless page opened from disk cannot reach the CDN reliably) and records `Annotations.parse`, Mermaid's own view of the arrows and `buildFlow` for every fixture in `packages/core/fixtures`. It is a migration tool, not part of `npm run verify`.
- **Version 3 reads the Mermaid sequence syntax itself** (`packages/core/src/sequence.ts`) instead of asking Mermaid for its parsed messages. The browser still renders with Mermaid, but the parser now runs in Node, in the skills' validator and in tests without a DOM, and arrows map to source lines directly. The goldens prove it reads participants, arrows, arrow styles and block nesting exactly as Mermaid 12.2.0 does for every fixture.
- **Six recorded differences from version 2**, each named in `packages/core/src/golden.test.ts`: (1) Mermaid's internal entity placeholders (`ﬂ°°59¶ß`) no longer leak into labels; `#59;` decodes to `;`. (2) A side part used twice on one step lists that step once. (3) `endings` are step indexes, not copies of step objects. (4) When Mermaid refuses the code, version 3 still reads participants and blocks and reports the exact line (`flow.syntax`), where version 2 fell back to a regex read. (5) The eight backend layer kinds the plan names (app, router, validator, controller, serializer, repository, eventbus, cron) are recognised, plus `dto`; version 2 on `main` knew ten kinds. (6) `main` is always present.
- **A bare `;` splits a line into statements**, because that is what Mermaid's lexer does (`A->>B: hi; B-->>A: ok` draws two arrows). Both scanners split the same way, so arrows and annotations stay paired. Text after a `;` that is not a statement is reported as `semicolon`.
- **Mermaid-incompatible lines are reported by the parser** as `flow.syntax` with the codes `semicolon`, `no-colon`, `unknown-line`, `block` and `keyword-alias` (the codes `validate.py` used), kept apart from the viewer's `flow.lint` so the lint shape stays identical to version 2.
- **Half-arrow styles (`-/`, `-|`, `-\`)** are parsed as arrows but typed as open arrows; Mermaid's exact LINETYPE numbers for them were not verified and no fixture uses them.
- **Demo flow error replies are drawn from App to API Client** (`APP-->>API: 401 Unauthorized`), not from the middleware or validator that produced them, so each reply pairs with the main request and shows as one of its endings. The step text says which layer produced the response.
- **The demo's in-memory database is described with the SQL it stands in for** in `@payload.sql` lines, each marked "an in-memory table, doing the job of", so the Data tab shows the tables touched without claiming the demo runs SQL.
- **`process.stdout.write` stays allowed.** The raw-HTML lint rule now bans only `document.write`/`writeln`, not every `.write(` call. It requires a pull request, an up-to-date branch, merge commits only, and the checks `verify`, `gitleaks`, `CodeQL (javascript-typescript)` and `CodeQL (actions)` (the CodeQL job is a matrix, so each language reports its own check). It also blocks force pushes and deletion. No required review, since GitHub does not let an account approve its own pull request. Renaming a job or the matrix changes the check names and must be mirrored in the ruleset.

## Phase 3: React viewer (2026-10-31)

- **The demo flow is the default diagram** (`examples/demo-store/flows/place-order.mmd`, imported at build time) and the "Load example" code, replacing the payment example version 2 shipped. The plan's section 8.12 asks for this; doing it now keeps one default for the rest of the build.
- **One parser for the viewer.** The page parses with `@swv/core` and uses Mermaid only to draw. Arrow N in the code is drawn arrow N, so the SVG mapping is by position, as in version 2, and a count mismatch shows a toast instead of guessing.
- **Mermaid output goes through DOMPurify** before it reaches the page, in the one component (`features/viewer/DiagramSvg.tsx`) the lint rule allows. The `name` attribute Mermaid puts on participants and the `<style>` element with the theme are kept; scripts, event handlers and links are not.
- **Content Security Policy:** `connect-src 'self' https: http://localhost:* http://127.0.0.1:*`, because Ask AI calls whichever model URL the user chose and Ollama runs on localhost over http. Scripts stay `'self'`.
- **Colours use `light-dark()`**, so every token is declared once and the theme choice only switches `color-scheme`. The user-interface theme follows the system, as in version 2; the diagram theme is the setting the user picks.
- **Feature folders own their screens; shared state lives in Zustand stores under `shared/state`.** Features talk through the stores (`ui` flags such as `askOpen`, `importOpen`) and never import each other; `dependency-cruiser` checks it. The one hand-over outside the stores is the right-click menu's "Ask AI: what is X?", which leaves the question in `sessionStorage` under `swv:ask:prefill`.
- **The keyboard map is the shell's** (`app/useGlobalKeys.ts`), including the Esc cascade in version 2's order; widgets handle only their local keys.
- **Version 2 behaviours kept as they really were, not as the README said:** `Home` goes to step 1 (the overview is reached with Esc or at load), and the Claude provider has no consent step of its own in the page (the host's prompt is the consent).

## Phase 11: structure review and threats (2026-10-31)

- **`@threat` is a step tag.** `%% @threat <high|medium|low> <short text>` belongs to the next arrow like `@unconfirmed`, and shows up as `step.threats` and `flow.threats`. A missing level or text is lint code `threat-format` and the line is dropped; text over 160 characters is `long-threat` and is still shown.
- **Seventh recorded difference from version 2** in `packages/core/src/golden.test.ts`: every step and flow has `threats`, and the "known tags" lint message names `@threat`.
- **Layer kinds fall back to participant names.** Most diagrams have no `@layer … kind=`, so the rules read the kind from a name such as `OrdersController` or `Payment Service`. Without this most rules could not run on most flows. A rule that still cannot run is listed as "Not checked" with the reason.
- **Rating points.** A high finding takes off 20, medium 10, low 5. One rule takes off at most twice its largest finding, so one habit repeated on many steps cannot sink the rating. The rating stops at 0. `@threat` lines never change it: they come from the diagram's author, and the rating comes only from the rules.
- **Confidence points.** Steps linked to code give up to 2, known layer kinds 1, flows reviewed in this browser up to 2 (2 flows give 1, 5 flows give 2). Unconfirmed details take off 1, or 2 when above 15% of the steps. A proposed design or a flow with no code links is always low. Otherwise 4 points or more is high and 2 or more is medium. The reasons are listed on screen.
- **`reply-missing` covers HTTP calls, outside calls and reads only.** The fast skill draws a reply only when a real value comes back, so a write with no reply arrow is normal and flagging it would be a false alarm.
- **A finding never repeats a secret.** It goes on screen and to the user's model, so query values and credential-like text are left out of what it says.
- **Threats column.** The step table's CSV gains a `Threats` column after `Unconfirmed`, and its Markdown "Also involved" cell gains `possible problem (level): text`. This is the one change to version 2's export shapes.
- **Explaining findings.** Plan section 5 sets no budget for this. It sends only the finding text (never the diagram code), for the 8 most serious findings at most, with 60 reply tokens per finding plus 20, so about 500 at most, in line with the day recap. The reply is words tied to finding numbers, validated with Zod and shown as plain text in its own block, so it cannot reach the rating.
